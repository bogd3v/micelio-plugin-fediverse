# Fediverse keys and algorithms

**Kind:** reference. What the fediverse plugin holds as a secret, what each key signs or encrypts, what rotating `ENCRYPTION_KEY` does to the actor key and which algorithms the plugin uses. The host's own secrets, policy and inventory are in `docs/security/keys.md` of `bogd3v/micelio-cms`; the plugin's rows are copied from there and the two must say the same where they overlap.

## Keys the plugin generates

| Key                                                             | Created by                                                                                | Where it is kept                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Rotation and exposure                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fediverse actor key pair (RSA-4096, RSASSA-PKCS1-v1_5, SHA-256) | `getActorKeyPairs` in `server/src/services/keys.ts`, on first use when the store has none | The Strapi core store (`strapi.store({ type: 'plugin', name: 'fediverse' })`, key `keyPairs`): the public JWK plain, the private JWK encrypted with `ENCRYPTION_KEY` (below). A plain entry from an older release is encrypted at boot (`encryptStoredActorKeys` in `server/src/services/keys.ts`). A second copy exists while a delivery is queued: Fedify writes the signing key into every outbox and fan-out message, and on PostgreSQL that is a row of `fedify_message_v2`, so the queue wrapper encrypts it with the same scheme (`server/src/utils/observed-queue.ts`) and the row is deleted when the message is taken for delivery | There is no rotation command, and the CMS does not rotate the key on upgrade. A database or a backup written after the upgrade alone does not let anyone sign as the blog; together with `ENCRYPTION_KEY` it does. Backups and free database pages written before the upgrade still hold the plain JWK ([below](#the-actor-key-written-before-encryption)). Deleting the stored entry makes the next use generate a new pair, which breaks the followers' copy of the old key ([architecture/federation.md](../architecture/federation.md#actor-key-at-rest)). |

The only secret the plugin reads from the host is Strapi's `ENCRYPTION_KEY` (`admin.secrets.encryptionKey`), which encrypts the actor's private key at rest and the key inside queued deliveries. The actor's public key is not a secret.

The random values of the actor key pair come from WebCrypto (`getActorKeyPairs` in `server/src/services/keys.ts`) and the IV of the encrypted envelope from `crypto.randomBytes` (`encryptText` in `server/src/utils/key-encryption.ts`).

## Rotating `ENCRYPTION_KEY`

With `FEDIVERSE_ENABLED=true` the actor's private key is encrypted with `ENCRYPTION_KEY`, so this value now also holds the blog's fediverse identity. After a change the stored key no longer decrypts and federation fails closed: the actor document and WebFinger answer `500`, an inbox delivery that needs a signed answer (the `Accept` of a `Follow`) answers `500` without sending it, and no outgoing activity is signed. Those answers carry only the generic body `Internal Server Error`, so a visitor cannot tell that the key is the problem. The cause, naming `ENCRYPTION_KEY`, is logged at `error` level at most once a minute, so crawlers that keep fetching the actor do not fill the log; the line never contains key material or a stack. The CMS never replaces the stored key on its own, so putting the old value back restores federation as it was. Tests: `test/fediverse-actor-key-encryption.test.ts` (actor, WebFinger and inbox answers, the `Accept` of a `Follow`, one log line per minute).

There is no re-encryption command yet. Until there is one, choose:

- **Queued deliveries.** A delivery waiting in the queue is encrypted with the old value and is dropped after a change (one `[fediverse]` error line a minute); the next publish queues new ones.
- **Keep the identity.** Do not rotate `ENCRYPTION_KEY` on an instance that federates unless it was exposed. After an exposure treat the actor key as exposed too, because whoever holds the database and the old value can sign as the blog.
- **Accept a new identity.** Change the value, then delete the core store row `plugin_fediverse_keyPairs`; the next request generates a new pair (see [The actor key written before encryption](#the-actor-key-written-before-encryption)).

**Strength.** The AES key is the SHA-256 of `ENCRYPTION_KEY`, with no key-derivation function, as in Strapi's own encryption service. That is adequate only because the value is a random secret of high entropy: use the 32 random bytes (256 bits) that `npm run generate:keys` of the host (`bogd3v/micelio-cms`) prints, never a password or a phrase, which a stolen database would let anyone guess offline. The boot checks length only (`src/utils/secrets.ts` in `bogd3v/micelio-cms`), not randomness. The IV is 16 random bytes, not GCM's usual 12: GCM accepts any IV length (it hashes a length other than 12 into the counter block), and with random IVs the collision bound stays far beyond the handful of encryptions a key pair ever gets.

## The actor key written before encryption

Encryption at rest protects what is written from the upgrade on. Everything written before it still holds the private JWK in plain text:

- database backups and dumps taken before the upgrade;
- free space in the database files: PostgreSQL keeps the old row version as a dead tuple until `VACUUM` reuses the space, and in its write-ahead log and any WAL archive; SQLite keeps the old page in the file's free pages until `VACUUM`.

So either destroy those copies (old backups, WAL archives, and a `VACUUM FULL` of `strapi_core_store_settings` in PostgreSQL or a `VACUUM` in SQLite), or treat the actor key as exposed.

Rotating the actor key is the only way to make an exposed one worthless, and it means a new federated identity: the actor id stays, but remote servers verify the blog's signatures with the copy of the old public key they cached until they fetch the actor again, so deliveries can be refused meanwhile and some servers may need followers to follow again. How each server reacts was not verified. The CMS does not rotate the key on upgrade; the operator decides, weighing who could have read the old copies against the cost to followers. To rotate, delete the core store row `plugin_fediverse_keyPairs`; the next request generates and encrypts a new pair.

## Crypto agility: accepted risk

ASVS V11.2.2 asks that algorithms and keys can be swapped. What the plugin does: stored actor keys are imported by their JWK type (RSA and Ed25519), the actor's `publicKey` is the first RSA pair, and the encrypted envelope carries a version and an algorithm (`v`, `alg`). What it does not do, on purpose:

- **Re-encrypt under a new `ENCRYPTION_KEY`.** There is no command; the choices are in [Rotating `ENCRYPTION_KEY`](#rotating-encryption_key).
- **Rotate the actor key and keep followers.** A new key is a new federated identity: remote servers verify with the key they cached until they fetch the actor again.
- **Choose the algorithm of a new pair by configuration.** It is the constant `NEW_KEY_ALGORITHM` in `server/src/services/keys.ts`; another type is a code change.

The risk is accepted because each of these changes the identity or the data of a live blog, which an operator should decide, and because no second key type is needed today. Revisit it when one is, or when a re-encryption command is written. The row is V11.2.2 of the host's ASVS mapping (`docs/security/asvs.md` of `bogd3v/micelio-cms`).
