# Fediverse log lines

**Kind:** reference. The inventory of what the fediverse plugin writes to the host's log: the `[fediverse]` lines, the security event `fediverse.inbox.signature-refused`, the personal data in them, and what is not logged. The host decides where the log goes and who reads it; this plugin adds no destination. The plugin's lines are copied into the host's own inventory (`docs/security/logging.md` of `bogd3v/micelio-cms`), and the two must stay identical where they overlap, because operators alert on them.

## Destination and format

The plugin writes through `strapi.log` only, so its lines follow the host's format and reach the host's transport, which is standard output by default. The fediverse library's own logging (LogTape) is configured by the plugin with one sink that calls `strapi.log` (`server/src/utils/fedify-logging.ts`), so its records reach the same transport and format; it adds no destination. In a host that logs one JSON object per line in production (as `bogd3v/micelio-cms` does), the metadata (`source`, `category`, `fedifyReason`, `event`, `outcome`, `path`, `reason`) is written as top-level fields next to `timestamp`, `level` and `message`; the development format prints the level and the message only. Who reads the output, and for how long, is the operator's platform.

### Fediverse activity

`info` lines for accepted and removed followers, unfollows, blocks, replies that were edited or deleted remotely, and the publication of an article or the profile (`server/src/federation.ts`, `server/src/services/publisher.ts`). `warn` lines for an ignored `Follow` or `Note` and a request guard that failed open (`server/src/federation.ts`). A `debug` line for an ignored reply is not written at the default level.

The actor key pair of a site is generated on the first use that finds none (`getActorKeyPairs` in `server/src/services/keys.ts`); the key material itself is never logged.

An `info` line `[fediverse] gave the default site N follower(s), N interaction(s), N federated article(s) and N actor key(s)` is written by the boot step that gives the default site what the plugin stored before the sites (`adoptDefaultSite` in `server/src/services/default-site.ts`), only when it changed something. It carries counts and nothing else: no actor id, handle or key. The rows made from the old `federatedArticles` store key are not in that count; `migrated N federated article(s) from the plugin store` reports them.

The 0.7 boot step (`runCutOver` and `ensureIdentifiers` in `server/src/services/cut-over.ts`) writes these lines, with no personal data (host names and slugs are the operator's own settings, public in the actor document):

- `info` `[fediverse] the default site's hosts are now <hosts>`: the hosts it pinned, once.
- `warn` `[fediverse] FEDIVERSE_HANDLE_HOST is ignored since 0.7 …`: a later boot that still finds the variable set.
- `info` `[fediverse] the host of FRONTEND_URL ("<host>") belongs to another site …`: the host it left out.
- `warn` `[fediverse] the site "<slug>" has no actor: its identifier "<identifier>" is another site's …`: a site whose slug another site's actor already uses.
- The error that stops the boot when another site holds the 0.6 handle host: `[fediverse] FEDIVERSE_HANDLE_HOST names "<host>", which another site already has as a host …` (or `URL` in place of the variable). It is thrown, not logged by the plugin, and names the variable and the host.

A `warn` `[fediverse] FRONTEND_DEFAULT_LOCALE is deprecated and read only because the site has no default locale …` is written once per process by `frontendDefaultLocale` in `server/src/services/articles.ts`.

### Personal data in these lines

- Remote handles (`@user@host`) and actor ids of followers appear in the fediverse lines (`server/src/federation.ts`). They describe people on other servers.
- The forwarded Fedify lines (`[fediverse] fedify.…`) carry remote actor ids, key ids and inbox URLs, path only (the query string is dropped). They are personal data, classed like remote followers in `docs/security/data.md` of `bogd3v/micelio-cms`.
- Remote text is cleaned before it is written (`cleanRemoteText` in `server/src/utils/remote-text.ts`).
- Error messages are written as the library produced them, and a message can repeat a submitted value (not verified for every library). In a host's production format the properties of an error, such as a database `detail`, are dropped by the host's formatter; this plugin does not control that.

## Security event: `fediverse.inbox.signature-refused`

The plugin writes one security event, `fediverse.inbox.signature-refused`, through `logSecurityEvent` in `server/src/utils/security-log.ts`: the message is `security: fediverse.inbox.signature-refused`, `warn` level, with the metadata `event`, `outcome` (`failure`), `path` and `reason`.

The fediverse plugin is a self-contained unit and does not import the host's `security-log.ts`: it keeps its own small copy with the same message, event string and field names (`event`, `outcome`, `path` with the same redactions, `reason`). It has no `client` field, so no hashed address either. The copy and the host's original (`src/utils/security-log.ts` of `bogd3v/micelio-cms`) must stay identical because operators alert on them.

| Event                               | Level  | Emitted by                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `fediverse.inbox.signature-refused` | `warn` | `server/src/federation.ts` (`mountFediverseMiddleware`): every `POST` to the shared or the actor inbox answered `401`. `reason` is `digest-algorithm` when the plugin refused it before Fedify because its `Digest` header has no SHA-256 or SHA-512 entry, `content-digest-not-covered` when it was refused before Fedify because a signature of its RFC 9421 `Signature-Input` does not cover `content-digest`, and `invalid-signature` for every `401` Fedify gives: a missing signature, a signature or digest that does not verify, a key that cannot be fetched, a signer that does not match the actor or the key, a failed integrity proof or nonce. Not throttled; the response is unchanged. Fedify's own line for the refusal carries the finer code as `fedifyReason` (rows above). Ordinary traffic produces this event all the time (for example a `Delete` from an actor whose server is gone ends in `keyFetchError` and a `401`), so alert on a change in its rate, not on raw counts |

The `path` is written with the query string and fragment dropped, percent-escapes decoded, then emails, IPv4 and IPv6 literals and token-like runs (16 or more characters with a digit) replaced by `[redacted]`, and cut to 200 characters (`MAX_PATH_LENGTH`). The `reason` is one of the closed set `InboxRefusalReason` (`digest-algorithm`, `content-digest-not-covered`, `invalid-signature`); a `path` that is empty after the redactions is left out. The function takes only the request path: no address, header, key id or signature is written. Logging never changes the answer.

## What is not logged

- Fedify's `debug` and `info` records (per-request detail, including the request headers and the activity of a refused delivery) and its `fedify.federation.http` access lines, which repeat the request line with the query string. A key fetch that fails is written only through the refusal that follows (`fedifyReason: keyFetchError`), because Fedify reports the fetch itself at `debug`. No property of a Fedify record is written, except `fedifyReason`.
- The response body of a refusing inbox, and the activity or comment text of a delivery.
- The actor's key material, and the `Digest` header of a refused delivery.
- Admin actions on the Fediverse page (block, unblock, retry) beyond the `[fediverse]` lines above: they carry ids and error names, no admin id. Admin audit is the host's.
